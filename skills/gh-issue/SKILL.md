# GitHub Issue Skill

## Goal

報告された問題やコード上の不備を調査し、曖昧さのない Issue 本文にまとめて GitHub に登録する。

## Inputs

* 問題の報告内容（エラーメッセージ、不具合の症状、要望など）
* 対象リポジトリ（未指定時は現在の作業ディレクトリのリポジトリ）
* 関連するコード・ログ・コミット履歴

## Outputs

* GitHub Issue（タイトル・本文・ラベル）
* 調査時に参照したファイル・行番号の一覧

## Workflow

1. **調査**: 報告内容を手がかりに該当コードを探索し、原因・再現手順・影響範囲を特定する。断定できない場合は「未確認」と明記し、憶測で断定しない。
2. **重複確認**: `gh issue list --search "<キーワード>"` 等で類似 Issue が既に存在しないか確認する。既存 Issue があれば新規作成せず、その旨を報告する。
3. **下書き作成**: 下記テンプレートに沿って Issue タイトルと本文を作成する。
4. **確認**: 作成前に下書き内容をユーザーに提示し、承認を得る。GitHub への Issue 作成は外部に公開される操作であり、無断で実行しない。
5. **登録**: 承認後、`gh issue create` で Issue を作成する。
6. **報告**: 作成された Issue の URL をユーザーに伝える。

## Issue Template

```md
## 概要
<問題の一文サマリー>

## 再現手順
1. ...
2. ...

## 期待される挙動

## 実際の挙動

## 調査結果
* 原因（判明している範囲）:
* 関連ファイル: `path/to/file.ext:123`
* 影響範囲:

## 環境
* OS / バージョン:
* 関連コミット:
```

## Rules

1. 曖昧語を使わず、再現手順・期待値・実際の挙動を具体的に書く。
2. コードを読んで裏付けが取れた事実と、未検証の推測を明確に区別する。
3. 既存 Issue の重複を必ず確認する。
4. `gh issue create` の実行前に必ずユーザーの承認を得る。
5. 秘密情報（トークン・認証情報・個人情報）を本文に含めない。

## Quality Checklist

* [ ] タイトルが問題を一文で表している
* [ ] 再現手順が第三者にも再現可能な粒度である
* [ ] 原因調査の結果と未検証の推測が区別されている
* [ ] 重複 Issue の確認を行った
* [ ] ユーザーの承認を得てから作成した

## Completion Criteria

* Issue が GitHub 上に作成されている
* Issue の URL をユーザーに報告済み
